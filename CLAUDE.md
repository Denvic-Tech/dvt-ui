# DVT Agent Guidelines

## Project Description

**DVT (Denvic Visual Transformer)** is a web-based ETL (Extract, Transform, Load) tool for visually designing, managing,
and executing complex data pipelines. The core of the application is a node-based graphical interface where users can
build data flows by connecting nodes that represent data sources, transformations, and data sinks.

This repository contains the **frontend system**, built with **React, TypeScript, Redux Toolkit, and Material-UI (MUI)
**. The graph editor is powered by **@xyflow/react**. The application is actively migrating to an autogenerated API
client that lives in `src/shared/gatewayClient`, replacing bespoke Axios wrappers.

**Key Concepts & Keywords:**

- **Visual ETL Pipeline:** The primary goal is to create data processing workflows visually.
- **Node-Based Editor:** The main UI is a canvas where users add and connect nodes. Each node represents an operation (
  e.g., load data, filter, join).
- **Data Sources:** Nodes can load data from various sources, such as databases (PostgreSQL, ClickHouse), and files (
  CSV, Excel, Parquet).
- **Data Transformations:** A rich set of nodes for data manipulation, including filtering, sorting, joining, pivoting,
  renaming columns, and executing custom Python code on dataframes.
- **Data Sinks:** Nodes can save processed data to databases or files.
- **Visual Extensions:** A core architectural feature. Each node type can have a custom React component for its
  configuration modal (`nodeExtensions`), providing a tailored user experience for setting parameters.
- **State Management:** Centralized state management is handled by **Redux Toolkit**, including graph state, UI state,
  and server data.
- **Data Schemas:** Data contracts and validation use **Zod**. Legacy definitions live in `src/schemas/`, but new work
  should colocate schemas inside the target FSD layer and plan migration.

## Node Extensions System

Node extensions let us attach bespoke UI and contextual tooling to individual nodes without touching the core graph
widget. The infrastructure lives in `src/app/providers/node-extensions`: `NodeExtensionsProvider.tsx` exposes a
singleton `NodeExtensionsRegistry`, `context.ts`/`hooks.ts` wire React consumers, and `lib/registry.ts` manages the
actual extension instances plus live subscriptions via `useSyncExternalStore`.

- **Provider wiring:** Wrap any surface that needs extensions with `NodeExtensionsProvider`. The default provider is
  already mounted high in the app tree, so features can call the hooks without extra setup. If you ever need an isolated
  set of extensions (for stories/tests), pass a custom registry instance through the `registry` prop.
- **Runtime usage:** `src/app/providers/node-extensions/hooks.ts:useNodeContentExtensions` subscribes to the registry
  and is consumed inside `src/widgets/custom-node/ui/index.tsx` to render `node_content_top`/`node_content_bottom`
  panels directly in each node card. Sister hooks (`useNodeModalExtensions`, `useNodeContextMenuItems`) power the
  configuration modals and context menus shown from the same widget.
- **Extension registry contract:** All implementations live in `src/node-extensions/<extensionName>/index.ts` and export
  a `NodeExtension` object with a unique `id`, human-friendly `name`, a `condition(nodeDefinition)` predicate, optional
  `order`, and a `type` (`'node_content_top' | 'node_content_bottom' | 'modal' | 'context_menu'`). Components receive
  the typed props declared in `lib/types.ts` (e.g., `NodeContentExtensionProps`, `NodeModalExtensionProps`).
  Context-menu extensions return menu items via `getItems`.
- **Authoring workflow:** (1) scaffold a new folder under `src/node-extensions` with any supporting UI. (2) Export the
  `NodeExtension` object from `index.ts` alongside the React component. (3) Register it once inside
  `src/app/providers/node-extensions/registry.ts` by adding it to the `nodeExtensionsRegistry.register(...)`
  call—registration order matters only when two extensions share the same `order` value. (4) Provide a narrow
  `condition` so the extension only activates for the intended `NodeDefinition`. Content extensions can render inline
  status badges, telemetry, etc.; modal extensions surface full-screen editors; context-menu extensions add actions
  backed by Redux dispatch via the `NodeContextMenuBuildContext`.
- **Extension import boundaries:** Treat each extension directory as a leaf slice. Files inside
  `src/node-extensions/<category>/<extension>/...` may import their own subtree plus shared FSD layers such as
  `src/shared`, `src/entities`, `src/features`, and the extension runtime in `src/app/providers/node-extensions`.
  They must not import reusable code from sibling extensions. Do not create new cross-extension folders like
  `src/node-extensions/common/*` or `src/node-extensions/*/shared/*`; move such code into the appropriate FSD layer
  instead.
- **Where shared extension code belongs:** Put pure serialization/parsing/type helpers into `src/shared/lib`, generic UI
  controls into `src/shared/ui`, and reusable node-editor blocks into `src/features/node/*`. Keep
  `src/node-extensions/*` only for extension-local code that is not shared outside that extension.
- **Testing & dynamic updates:** Because the registry exposes `register`/`clearAll`, you can mount a temporary provider
  inside tests to assert rendered extensions. Hooks rely on `useSyncExternalStore`, so hot module replacement or runtime
  registration (e.g., lazy-loaded bundles) is safe and causes `useNodeContentExtensions` consumers to re-render when the
  registry changes.

## Tech Stack & Tooling

- **Runtime:** React 18, React Router v7, Redux Toolkit 2.6 with `redux-persist`, TypeScript 5.6, Vite 6, MUI 6, React
  Hook Form, Zod, Axios, and `@xyflow/react`.

  `src/shared/gatewayClient`.

## Architecture Layers

The project is being reorganized around Feature-Sliced Design (FSD). Focus new work inside the layers below and migrate
legacy code toward them when feasible.

- `src/shared/`: Cross-cutting foundations (design tokens, utility libs, autogenerated clients such as `gatewayClient`,
  shared types).
- `src/app/`: Application-level composition (providers, router, store setup, global configuration, initialization
  flows).
- `src/entities/`: Domain primitives with state slices, services, and UI primitives scoped to a single business entity (
  e.g., projects, graph, db-connection, pipeline metadata).
- `src/features/`: User stories built from multiple entities (e.g., manage graph connections, sync graph workflows).
- `src/widgets/`: Ready-to-use UI blocks assembling features into self-contained experiences (e.g., `graph-editor`
  widget).
- `src/pages/`: Route-level screens composed from widgets and features.

`public/` contains static assets copied to the build output, and `dist/` holds the production bundle (gitignored).

### Feature-Sliced Structure & Import Rules

```
src/
├── app/              # Providers, router, store, global UI scaffolding
├── entities/         # Business primitives (projects, queue, storage, nodeDefinition, etc.)
├── features/         # User-facing flows composed from entities
├── widgets/          # Route-ready UI blocks
├── pages/            # Router-level screens
├── shared/           # Design system, gateway client, utilities, errors
├── contexts/         # React contexts (e.g., AuthContext)
├── helpers/          # Legacy helpers awaiting migration
└── hooks/            # Legacy custom hooks awaiting migration
```

- Lower layers must never import from higher layers; entities stay independent inside their model layer.
- Prefer colocating schemas, hooks, and UI next to the owning FSD slice instead of central barrels.
- Path alias `@/` maps to `src/` (see `vite.config.ts`), so reference shared utilities as `@/shared/...` rather than
  deep relative paths.

### Autogenerated API Client

- The backend contract is consumed through a generated SDK exposed from `src/shared/gatewayClient`.
- Prefer calling gateway client methods over legacy `services/api.ts` wrappers; new endpoints should be wired through
  code generation.
- If the generated client misses an endpoint or type, extend the OpenAPI spec and regenerate instead of hand-writing
  HTTP calls.

### Legacy Modules Pending Cleanup

The following directories are considered legacy. Only touch them when migrating code, and prefer moving functionality
into the new FSD layers.

- `src/helpers`
- `src/hooks`
- `src/schemas`

## State Management & Async Patterns

- Redux store lives under `src/app/providers/store/` with `rootReducer.ts` defining ~22 slices.
- `redux-persist` whitelists `global` and `nodeProcessor`, while `alerts`, `websocket`, `nodeDrawer`, and API slices
  stay transient.
- Middleware order matters: `errorListenerMiddleware` → `syncGraphMiddleware` (debounced graph batching) → default RTK
  middleware → `websocketMiddleware`.
- Persisted client-side UI preferences should go through `src/entities/ui-preferences` instead of ad hoc `localStorage`
  calls inside components. Use this entity for durable interface choices such as `/projects` view mode and suppressible
  `Больше не спрашивать` decisions.
- Keep `ui-preferences` focused on browser-only user preferences. Do not mix it with domain entities like `projects`; if
  a preference later becomes server-backed, promote it into a dedicated user/settings flow instead of expanding direct
  localStorage usage.

### `createAppAsyncThunk` Standard

- Always import thunks from `src/app/providers/store/helpers.ts`.
- The helper wires `AppAsyncThunkConfig`, guarantees `ApiError` shaping, and exposes `mapUnknownError` so reducers
  receive typed `ApiErrorPayload`.
- Never fall back to bare `createAsyncThunk`; mismatched error payloads will break reducers and listeners.

### Standard Entity Layout

```
entities/<entity>/
├── api/<entity>Api.ts          # Pure gateway client wrappers
├── model/
│   ├── slice.ts                # Slice + thunks using createAppAsyncThunk
│   ├── selectors.ts / hooks/   # Memoized selectors + custom hooks
│   └── listener.ts             # Optional listener middleware
├── ui/                         # Entity-scoped components
└── index.ts                    # Explicit exports
```

- Register new slices in `rootReducer.ts` and wire extra middleware inside `src/app/providers/store/store.ts` only when
  required.

## Graph Synchronization Pipeline

- Graph edits enqueue operation objects (Create, Delete, Select, Position, Replace, InputData, DisplayName, Comment)
  with metadata.
- Queue aggregates operations by node ID, merging redundant updates (for example, multiple position tweaks collapse into
  one) via helpers such as `src/helpers/deepMerge.ts`.
- `syncGraphMiddleware` debounces flushes (default 2 s) before calling `flushGraphOperations`.
- `flushGraphOperations` packages the aggregated outbox and posts it via the gateway client, returning
  `{ ackedIds, response }`.
- Listener middleware handles retries with exponential backoff (up to 30 s) so transient network issues do not drop
  edits.

## Routing & Authentication

- Core routes live in `src/App.tsx`, using `ProtectedRoute` to guard private areas.
- Flow: `/` and `/project-editor/:projectID` require auth; `/sign_in` is accessible when logged out.
- Authentication is handled through `src/contexts/AuthContext.tsx` instead of Redux to avoid persisting sensitive data.
  On app mount it calls `client.auth.checkAuth.post()`, caches auth state in context, and `ProtectedRoute` consults
  `isAuthenticated`.

## Real-Time & WebSocket Integration

- `src/config.ts` derives WebSocket URLs (ws/wss) from `VITE_API_BASE_URL`.
- WebSocket-specific state lives in `src/entities/websocket/`, while message dispatch logic sits in
  `src/shared/wsMessageActions.ts`.
- `websocketMiddleware` routes inbound messages to domain slices, keeping Redux as the single source of truth.

## Theming & Design System

- Global theme configuration: `src/shared/theme.ts`.
- Color tokens and icon registries: `src/shared/colors.ts` and `src/shared/icons.ts`.
- `src/app/ui/common/ThemeWrapper` mounts the theme provider; keep any design tokens in `shared`.
- UI дизайн должен следовать стилю Clean Minimal, описанному в `style_reference/CleanMinimalDesignSystem.md`.

## Shared Monaco Code Editor

The shared Monaco foundation lives in `src/shared/ui/code-editor`. Use it for any new multiline/code-like editor instead
of mounting `@monaco-editor/react` directly inside node extensions. Node-specific code should pass data and completion
catalogs into the shared layer; editor behavior, styling, key handling, markers, layout fixes, and completion wiring
belong in `shared/ui/code-editor` or a reusable language pack.

- **Base component:** import `CodeEditor` and related types from `@/shared/ui/code-editor`. It provides the Clean
  Minimal
  shell, scoped completion registration for the active Monaco model, stable layout in modals, markers, Tab completion,
  and plain `Enter` as newline.
- **Existing adapters:** use `PythonCodeInput` for Python snippets and `TemplateMonacoInput` for template-aware text
  inputs. `TemplateMonacoInput` supports `completionProviders` for top-level hints while keeping `{{...}}` expression
  autocomplete isolated from node/dialect hints.
- **Dialect extensions:** implement a `CodeEditorCompletionProvider<TContext>` that returns ordered sections from
  `getSections`. Keep parsing/ranking logic in a language pack such as
  `src/shared/ui/code-editor/language-packs/sql.ts`, not inside a concrete node modal.
- **SQL metadata:** for SQL editors, build a `SqlCompletionCatalog` from available node metadata and pass
  `createSqlCompletionProvider(...)` through `TemplateMonacoInput.completionProviders`. Avoid passing a flat mixed list
  of Monaco suggestions when the language needs context-aware sections like columns after `SELECT` and tables after
  `FROM/JOIN`.
- **Completion UX contract:** custom hints should be sectioned and shown before/default-separated from Monaco defaults;
  applying suggestions is done with `Tab`; insertion ranges must target the current caret word/range, not append text to
  the end of the value.
- **Stability guardrails:** do not create new empty arrays/objects inline for `completionProviders`,
  `additionalSuggestions`, or `markers` defaults because Monaco can re-register providers and reset suggest-list
  navigation. Reuse module-level empty constants or memoized values.
- **Where not to customize:** do not add feature-specific keyboard hacks, suggest widget patches, or Monaco global
  options in individual node extensions. If a node reveals an editor UX bug, fix the shared editor or a language pack so
  other nodes benefit and regressions stay testable.

## Agent Task Management (`AGENTS_TASKS.md`)

The `AGENTS_TASKS.md` file is used to list pending development tasks for the AI coding agent. Tasks in this file should
be clear, actionable, and self-contained. The agent will only execute tasks from this file upon explicit user request,
such as "Complete all tasks from AGENTS_TASKS.md".

## Agent Changelog (`AGENTS_CHANGELOGS.md`)

The `AGENTS_CHANGELOGS.md` file serves as a log for all modifications made by the AI coding agent. After completing any
task or making changes to the codebase, the agent must append a new entry to this file.

Each entry must include:

- The date and time of the change (in `YYYY-MM-DD HH:MM:SS` format).
- A clear and concise description of the changes made.
- **All changelog entries must be written in Russian.**

Example entry:

```markdown
### 2024-08-01 15:30:00

- Обновлен файл `AGENTS.md` для улучшения описания проекта и структуры.
- Добавлены инструкции по ведению файлов `AGENTS_TASKS.md` и `AGENTS_CHANGELOGS.md`.
```

This process ensures a transparent and traceable history of automated code modifications.

### Agent Knowledge Base (`AGENTS_TIPS.md`)

The `AGENTS_TIPS.md` file is a self-maintained knowledge base for the AI agent. If an agent encounters and solves a
complex problem, discovers a useful pattern, or develops a reusable code snippet, it should document the solution or
finding in this file. The agent should consult this file when starting new tasks to check for relevant information that
could accelerate its work.

## File System Access

For working with the repository file system, the agent must use the `filesystem` tool (read/write/list/edit) as the
primary interface instead of shell commands where possible. Use shell commands only when the `filesystem` tool cannot
perform the required operation.

## Build, Test, and Development Commands

- `npm install` prepares dependencies.
- `npm run dev` starts Vite at http://localhost:5173 with hot reload.
- `npm run dev:env` boots the dev server with `.env` explicitly loaded for debugging env mismatches.
- `npm run build` runs `tsc -b` then `vite build`; execute before merges.
- `npm run preview` serves the built bundle for smoke checks.
- `npm run lint` / `npm run lint:fix` enforce ESLint; `npm run format` / `npm run format:check` apply Prettier.
- `npm run generate:gateway` regenerates the SDK (requires `VITE_API_BASE_URL`).
- `npm run test:run` executes Vitest (see Testing Guidelines for Windows-specific ESBuild notes).

## Coding Style & Naming Conventions

- Prettier (see `.prettierrc`) enforces 2-space indent, semicolons, single quotes, 80-char width, and LF endings; let
  the formatter run before committing.
- React components belong in PascalCase `.tsx` files; hooks remain in `camelCase` and should live within the
  corresponding FSD slice.
- Prefer named exports; keep import paths explicit instead of barrel re-exports.
- ESLint extends JS + TS + React configs; never merge with `no-undef` or lint warnings.

## Testing Guidelines

- Use `npm run test:run` for Vitest. On Windows set `ESBUILD_BINARY_PATH` to
  `node_modules/vitest/node_modules/@esbuild/win32-x64/esbuild.exe` to match Vitest's bundled esbuild (example:
  `$env:ESBUILD_BINARY_PATH='C:\\work\\projects\\dvt_ui\\node_modules\\vitest\\node_modules\\@esbuild\\win32-x64\\esbuild.exe'; npm run test:run`).
- While adding features, include a testing plan in the PR and, where feasible, ship component-level checks under
  `src/<area>/__tests__/` using Vitest conventions (`Component.test.tsx`).
- If tests still fail with `spawn EPERM`, run the same command from an unrestricted local shell or ensure the OS policy
  allows executing `node_modules/@esbuild/win32-x64/esbuild.exe`. When using this agent in a sandboxed environment, ask
  the user to disable sandbox restrictions for test runs so the esbuild binary can be spawned.
- Use Playwright MCP tool for visual testing. Configure authenticated test sessions through local environment
  variables such as `CODEX_DVT_EMAIL` and `CODEX_DVT_PASSWORD`; never commit real credentials or session secrets.
- The project-level Playwright MCP profile is stored in `tmp/playwright` via `.codex/config.toml` (
  `--user-data-dir tmp/playwright`), so browser state for this repo should be persisted there between Playwright MCP
  restarts.

## Commit & Pull Request Guidelines

- Follow existing convention: uppercase verb prefixes (`ADD`, `FIX`, `UPD`) plus a brief subject (`FIX useCacheApi`).
- Keep commits scoped; separate refactors from behavior changes.
- PRs must describe problem + solution, list validation steps (build/lint), attach UI screenshots or recordings, and
  link tracking tickets.
- Request review from the owning squad and wait for green checks before merging.

## Environment & Configuration

- `src/config.ts` reads `VITE_API_BASE_URL`; define it in `.env.local` (not committed) to target the backend. WebSocket
  URLs derive automatically, so verify the host is correct per environment.
- SDK generation outputs to `src/shared/gatewayClient`; when regeneration is required, rely on the provided `openapi-ts`
  tooling instead of manual edits.
- Keep secrets or keys outside the repo and document required env variables in the PR.

## Development Workflow & API Client

- When introducing a feature, build it bottom-up: create an entity scaffold, write its API layer around the gateway
  client, add a slice with `createAppAsyncThunk`, register it in `rootReducer`, and only then compose the
  feature/widget/page.
- Apply listener middleware sparingly; if required, co-locate it under the owning entity.
- API layers should surface domain-level helpers while throwing `ApiError`; let thunks translate those errors for
  reducers.

### API Client Regeneration

1. Confirm the backend exposes an up-to-date OpenAPI document at `${VITE_API_BASE_URL}/openapi.json`.
2. Run `npm run generate:gateway` (requires env vars) to refresh `src/shared/gatewayClient`.
3. Address new TypeScript diagnostics in app code; generated files are auto-suppressed but you must fix consumer errors.
4. Use `DEBUG_TSC_SUPPRESSED=1 npm run build` to view suppressed diagnostics when investigating generation issues.

### Performance & Reliability Guardrails

- Graph syncing uses a 2 s debounce plus aggregation to avoid flooding the API while keeping the editor responsive.
- Selective persistence keeps only `global` and `nodeProcessor`, preventing websocket/auth artifacts from leaking to
  disk.
- Memoized selectors inside entities reduce unnecessary re-renders; follow Reselect patterns.
- Listener middleware + exponential backoff replace polling for real-time pathways.
